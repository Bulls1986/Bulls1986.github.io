<h2 id="current-published-baseline">Current published baseline<a class="anchor" aria-hidden tabindex="-1" href="#current-published-baseline">#</a></h2>
<p>The latest stable release verified by this guide is <a href="https://github.com/Bulls1986/Inkiva/releases/tag/v0.6.0" class="link">Inkiva v0.6.0</a>, published on 2026-10-29. Its tag-triggered workflow built and smoke-tested Windows x64, macOS Intel x64 and macOS Apple Silicon arm64 packages, verified updater metadata, assembled checksums and published 14 assets.</p>
<h2 id="release-model">Release model<a class="anchor" aria-hidden tabindex="-1" href="#release-model">#</a></h2>
<ul>
<li>A pushed tag matching <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>v*</span></span></code></span> starts the <strong>Release Inkiva</strong> workflow.</li>
<li>The first job validates the tag as SemVer with a leading <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>v</span></span></code></span>.</li>
<li>Stable tags publish a normal GitHub Release. Tags containing a hyphen, such as <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>vX.Y.Z-rc.1</span></span></code></span>, are marked as prereleases.</li>
<li>Supported release targets are <strong>Windows x64, macOS x64 and macOS arm64</strong>. Linux and Windows ARM64 are not release targets.</li>
<li>The release job assembles the already-built platform artifacts, validates updater metadata and checksums, creates a draft release with assets, then promotes it to a published release.</li>
</ul>
<p>Do not create a GitHub Release manually or upload platform artifacts outside this workflow.</p>

<p>Inkiva currently uses <strong>squash merge only</strong>. Merge only when explicitly authorized. A PR being mergeable is not evidence that its checks passed.</p>
<h2 id="3-merge-and-create-the-release-tag">3. Merge and create the release tag<a class="anchor" aria-hidden tabindex="-1" href="#3-merge-and-create-the-release-tag">#</a></h2>
<p>After the candidate PR is merged:</p>
<ol>
<li>Verify GitHub reports the PR as merged.</li>
<li>Fetch the authoritative remote <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>develop</span></span></code></span> ref and verify it points to the expected merge commit.</li>
<li>Create the annotated stable tag on that exact approved commit.</li>
</ol>

<p>The tag push is the publication trigger. Do not tag a local candidate branch before its approved changes are integrated into the intended release commit.</p>
<p>For a release candidate, use a prerelease tag such as <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>vX.Y.Z-rc.1</span></span></code></span>. The workflow marks hyphenated tags as prereleases and skips the stable updater-artifact contract; the final stable tag must still pass the full stable release checks.</p>
<h2 id="4-what-the-tag-workflow-does">4. What the tag workflow does<a class="anchor" aria-hidden tabindex="-1" href="#4-what-the-tag-workflow-does">#</a></h2>
<p>The current workflow performs these stages:</p>
<ol>
<li><strong>Validate tag</strong> — enforce the supported SemVer tag format.</li>
<li><strong>Build matrix</strong> — build Windows x64, macOS x64 and macOS arm64 packages on their native runners.</li>
<li><strong>Package smoke</strong> — validate the already-built Windows installer/ZIP and macOS DMG/ZIP artifacts. Smoke consumes downloaded build artifacts; it does not rebuild the application.</li>
<li><strong>Assemble release artifacts</strong> — merge the two macOS <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>latest-mac.yml</span></span></code></span> metadata files, reject duplicate artifact names and create <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>SHA256SUMS.txt</span></span></code></span>.</li>
<li><strong>Verify stable updater artifacts</strong> — for stable tags, require the tag to match the desktop package version and verify required Windows/macOS updater files, metadata versions, SHA-512 values, file sizes and SHA-256 checksum entries. Prerelease tags skip this stable updater-channel contract.</li>
<li><strong>Compose release notes</strong> — generate GitHub's merged-PR notes and append checksum verification plus unsigned macOS installation guidance.</li>
<li><strong>Publish</strong> — create a draft release with all assembled assets, then promote it to a published release.</li>
</ol>

<p>The manifest contains checksums for the 13 other release assets; it does not hash itself. Confirm that both updater metadata files describe the tag version and that the release body includes checksum instructions and the unsigned macOS disclosure.</p>
<p><strong>macOS distribution:</strong> current builds are unsigned and not notarized because the project has no Developer ID signing identity. Gatekeeper may block the first launch. Only install a release you trust; in Finder, Control-click the app and choose Open, then confirm the prompt. Do not disable Gatekeeper globally.</p>
<p>Package smoke is not a substitute for native macOS manual acceptance, reference-machine absolute performance qualification, or a real installed-app upgrade/document-preservation test. Record those separately as passed, deferred or risk-accepted based on actual evidence.</p>
<h2 id="6-website-deployment">6. Website deployment<a class="anchor" aria-hidden tabindex="-1" href="#6-website-deployment">#</a></h2>
<p>The separate <strong>Deploy Inkiva website</strong> workflow is triggered by a published GitHub Release and by relevant changes on <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>develop</span></span></code></span>. On the release event it builds the static website and deploys it to the configured Pages repository.</p>
<p>The website resolves its displayed release label from the latest published GitHub Release through <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>packages/website/next.config.ts</span></span></code></span>; it does not rely only on the package manifest version. After publication, verify the corresponding <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>website-deploy.yml</span></span></code></span> run succeeds.</p>
<h2 id="7-post-release-records">7. Post-release records<a class="anchor" aria-hidden tabindex="-1" href="#7-post-release-records">#</a></h2>
<p>After publication:</p>
<ul>
<li>Update <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>packages/website/content/docs/CHANGELOG.md</span></span></code></span> with the user-visible release summary.</li>
<li>Update the release-readiness audit with the exact tag commit, workflow run, asset inventory, updater/checksum result and any accepted qualification gaps.</li>
<li>Keep manual acceptance, reference performance and upgrade evidence distinct from package-smoke/CI evidence.</li>
<li>Do not automatically bump <span data-rehype-pretty-code-figure=""><code data-language="plaintext" data-theme="github-dark-dimmed github-light" class="inline"><span data-line=""><span>develop</span></span></code></span> to a new development version unless a separately approved next-version plan requires it. Keep the three package manifests aligned.</li>
</ul>
